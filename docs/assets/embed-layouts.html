把自己的问数服务接进 Quick BI，位置不止「看板旁边」一种。下面三张是示意图——画的是区域的归属和边界，不是产品截图。

灰蓝 = Quick BI 平台的地盘，品红 = 你的服务的领地。看颜色就能判断谁在谁里面。

  • 像「旁边一个独立区域」吗？就是这个 左右分栏，问数是常驻的窄栏，看板是主区。
  • 代价：外壳页面、登录态、看板嵌入 ticket 都得自己做；走 JS SDK 还要求 Quick BI 专业版。

  • 好处：整页都是你的，交互最自由；门户菜单能统一管权限入口。

三种摆法都要过的关

不管选哪种，下面几条是硬约束，面试被追问「落地时踩过什么坑」可以直接讲。

必须 HTTPS iframe widget

内嵌页面控件的地址必须以 https:// 开头，http 页面直接不给嵌。

对方可以被嵌 X-Frame-Options

你的服务如果返回 X-Frame-Options: DENY 或限制性 CSP，页面上就是一片空白——不是配置错了，是被浏览器拦了。

跨域 / Cookie 校验 403

嵌入页会和发起页校验 Header 与 Cookie 是否一致。用域名而不是 IP 访问，且后缀与系统域名保持一致。

不联动 filter

内嵌内容与看板的筛选、联动相互隔离。想让问数「知道用户在看哪个店铺」，得自己传参，不能指望看板给。

平台自己二选一 小Q

官方说明：通过增强嵌入方案嵌到第三方系统的仪表板，不支持仪表板小Q问数。两条路平台已经帮你分开了。

权限口径要自己对齐 RLS

小Q 走 Quick BI 的行级权限，你的服务走 X-API-Key + 授权店铺配置。两套体系下同一人看到的数可能不一致——这才是真正要提前想的问题。
