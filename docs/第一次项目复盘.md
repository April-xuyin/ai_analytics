## intent parser   意图解析

### 百炼解析：app/intent/bailian.py

#### *职责：用大模型把中文问题 **解析成结构化意图** （`QuestionIntent`）。它是"LLM 解析器"的通用实现——走 OpenAI 兼容接口，默认连阿里百炼。

问题 + 相关元数据 → 拼成 prompt → 交给模型 → 模型返回 JSON → 转成 QuestionIntent

#### *接收什么

1. 构造时，接收元数据对象、可选的client（配置好的客户端对象即API配置)和model（模型）[没有的话，API_KEY 必须手动配环境变量（URL、MODEL 有默认值）]
2. 运行时，接收字符串形式的问题

#### *输出什么

1. 构造完，输出：**对象上有 `catalog`、`model`、`client` 三个属性；缺 key 就抛 `BailianConfigError`**
2. 运行后返回**一个 `QuestionIntent` 对象**

#### *为什么需要它

1. **不用写死关键词规则** 。把用户问题原样丢给大模型，让模型自己理解意思。用户说"卖了多少钱""销售额""销售收入"都能理解，靠写 if-else 是写不完的。
2. **接口跟供应商解耦** 。输出统一是 `QuestionIntent`，换大模型供应商可以直接复用。

## 明确安全边界，相关问题回答

### 为什么 DeepSeek 不直接执行 SQL？


* 大模型执行SQL有很强的不可控性，~~用户的问题千奇百怪~~，如果不框定白名单，大概率得不到想要的答案（模型输出需要经过程序控制和校验）

> 让模型直接生成并执行SQL，会带来表选错、指标口径错误、粒度错误、越权访问和危险SQL等风险

### 模型输出未知指标会发生什么？

* 找不到对应的元数据、数据集（不一定在元数据阶段直接报错）

> 当前流程中，未知指标会导致
> safesqlgennerator 找不到对应的指标或模板
> ➡️返回unsupported ➡️不执行SQL

### 为什么只能查询 6 张白名单表？

方便首批链路的完整跑通，另外限定用户只能查我们提供的表，可以更快速的找到他们要的结果

> 主要原因是安全和可控
> 只开放已经治理过的表
> 避免访问ODS/DWD敏感明细
> 控制模型选表范围
> 降低SQL粒度和重复计算错误
> 便于评测和排查

### DROP TABLE 在哪里被拦截？

local_runner.py

> local_runner.py
> safesqlgenerator:只生成已登记的select模板
> localqueryrunner：最终拦截drop、delect、update等危险语句

### 为什么限制返回行数？

提升查询速度，减少结果冗余

### API Key 为什么放在 .env？

方便读取

> 把密钥和代码分离，避免密钥写死在代码中或者提交到git。
> 生产环境应使用 云secret manager、环境变量或者密钥管理服务

### 为什么真实 Parquet 不提交 Git？

~~在本地先跑通可以不联网，最小成本~~

> 测试阶段：真实业务数据可能包含敏感信息
> 文件较大，不适合git
> 数据可能过期
> 防止上传公司数据
> 避免仓库被真实数据污染

### * 一条问题如何得到答案

用户输入的问题会转为问题字符串，程序会执行元数据检索，把元数据交给解析器检索，大模型会返回json形式的问题意图解析（包含指标名，~~数据集~~，维度等），接收到意图后根据白名单限制进行SQL输入，SQL查询出数据结果，最终问题/查询状态/SQL/行数/检索痕迹会给打包成对象返回，再以Json形式返回

> 用户输入自然语言问题后，程序先通过 `loader.py` 从指标、数据集和业务术语等 YAML 元数据中检索与问题相关的业务知识，再将问题和检索结果交给 DeepSeek，由模型把自然语言解析成结构化的 `QuestionIntent`，包括指标、维度、时间范围、排序和数量等信息；`QuestionService` 接收到意图后交给 `SafeSqlGenerator`，根据白名单指标、维度和受控 SQL 模板生成查询语句，而不是让模型直接执行任意 SQL；随后 `LocalQueryRunner` 对 SQL 做只读和安全校验，并调用 DuckDB 查询本地 Parquet 数据，最后将查询结果、查询状态、指标口径、数据时间范围、数据来源和 SQL 等信息封装成 `AnalyticsAnswer` 返回；如果指标不明确、数据集不存在或当前没有对应的安全 SQL 模板，系统会要求用户补充信息或明确提示暂不支持，而不会直接猜测或执行查询。

> 用户输入问题后，系统先从指标口径、数据表说明和业务术语中检索相关知识，再调用大模型识别用户想查询的指标、维度、时间范围和筛选条件。随后，系统根据预先配置好的指标和数据权限生成受控查询语句，并进行只读校验，确保只访问允许的数据、不会执行修改操作。查询通过本地分析引擎执行，生产环境则会切换到 MaxCompute，最后系统将结果、指标口径、统计时间和数据来源整理后返回给用户。如果问题含义不明确、数据不支持或没有对应的安全查询逻辑，系统会主动追问或提示暂不支持，而不是直接猜测。

### 每个模块的职责

loader.py：把整理好的数据集,指标解析,指标术语的yaml文件加载进内存，作为元数据底座

`→ 加载并检索 YAML 元数据`

bailian.py和deepseek.py：把用户问题解析成程序认识的意图形式（列表)，不让模型直接生成SQL

`→ 调用模型，把问题解析成结构化意图`

intent/model.py:承接固定形式的意图

`→ 定义 QuestionIntent`

service.py:把意图接进来，再调用generator.pyq去生成SQL，最后交出结果对象

`→ 编排元数据、意图、SQL 和查询结果`

generator.py：把意图拼接为SQL（白名单限制SQL，不能drop等修改，只能select）

`→ 根据受控意图生成安全 SQL，不是任意拼接 SQL`

local_runner.py:调用duckdb查询SQL，返回行列形式结果

`→ SQL 只读检查、白名单视图注册、DuckDB 执行`

question/model.py:输出固定形式结构的结果

`→ 定义 AnalyticsAnswer`

### 为什么采用受控 Text-to-SQL：

不限制的由大模型直接去产生SQL，产出的不一定是我们想要的，随机性太大

> 受控Text_to_SQL 将模型的自然语言理解能力和程序的安全执行能力分离，既保留灵活问数能力，又降低错误SQL、越权和口径错误风险

### 当前安全措施：

~~问题澄清~~；找不到元数据、数据集、白名单即报错终止

> 数据集白名单；
> 只允许select/with；
> 拦截DROP/DELETE/UPDATE等增删改语句；
> 限制返回行数；
> SQL只从安全模板生成；
> 指标必须存在于元数据；
> 未支持意图返回unsupported；
> API KRY不进入代码和git

### 当前限定：

限定意图的格式，由大模型去解析意图，再按照白名单限制的格式去产出SQL（限定只能查询，不能做增删改的操作），产生的回答也按照限定格式产出
