# Amazon US AI 智能问数项目：总览与实施路线

> 本文是项目目标、范围、阶段和进度的唯一基准。开始新工作前先确认本文的“当前阶段”和“下一步”；目标、顺序或验收口径发生变化时，必须先更新本文，避免把可演示 MVP 误当成最终项目。

## 1. 最终目标

基于 VG AWS 数仓，构建一个面向 Amazon 运营人员的企业内部智能问数系统，并按照“小公司可真实落地”的标准完成。

业务人员在 Web 页面输入自然语言问题，例如：

- 最近 30 天销售额排名前 3 的店铺是什么？
- 近一周整体退款率是多少？
- 2026 年 8 月销售额最高的 10 个 SKU 是什么？
- 上架满 30 天但销量没有达到 20 单的 SKU 有哪些？

系统应返回查询结果、指标口径、数据时间和可追溯 SQL；问题信息不足时主动澄清，超出数据或权限范围时明确拒绝。

项目同时用于学习 Python 和 AI 应用开发，并作为从数据开发工程师转向 AI 开发工程师的简历项目。

### 最终完成标准

只有同时满足以下条件，才进入最终简历整理：

1. 常用经营问题不依赖“一题一个 SQL 模板”，能够组合指标、维度、时间、筛选、排序和 TopN；
2. 复杂业务问题允许保留经过评测的专用模板，例如北极星目标和 SKU 生命周期；
3. DeepSeek 只解析结构化意图，不直接执行 SQL 或决定数据权限；
4. 元数据检索能召回相关指标、数据集、字段、术语和标准示例，并有检索评测；
5. SQL 只能访问白名单数据，经过权限注入和可靠的只读安全检查；
6. DuckDB 本地结果和 MaxCompute 云端链路均通过验收；
7. 评测覆盖意图、SQL 执行、结果正确性、澄清、拒答、越权、耗时和成本；
8. Web 能以适合运营人员的方式展示表格、图表、口径和必要的查询依据；
9. 具备认证、店铺级权限、审计、监控、超时、日志轮转、容器化和部署/回滚说明；
10. 明确记录已知限制，不把“本地生产模拟”描述为“已在 ECS 正式上线”。

## 2. 项目范围

### 本项目包含

- Amazon US 经营分析；
- 品牌、店铺、SKU、ASIN 和时间等维度；
- 销售额、订单数、销量、退款、高价值订单、SKU 生命周期等指标；
- DeepSeek 结构化意图解析；
- 元数据驱动的受控 Text-to-SQL；
- RAG、SQL 安全、权限、评测、API 和 Web；
- DuckDB/Parquet 本地开发环境；
- MaxCompute 云端查询环境；
- Docker、Nginx、审计、监控和 ECS 迁移方案。

### 第一版不包含

- 自动修改 MaxCompute、DataWorks 或业务数据；
- 开放查询全部 ODS/DWD 明细表；
- 复杂预测模型；
- 多 Agent 自主协作；
- 模型微调。

只有在积累足够高质量样本，并通过评测确认 Prompt、语义层和 RAG 仍存在稳定瓶颈后，才考虑微调。Agent 不是当前目标所必需的能力。

## 3. 目标架构与当前差距

### 最终目标链路

```text
运营人员 Web
    ↓
Nginx 统一入口
    ↓
FastAPI：认证与请求校验
    ↓
语义检索：指标、维度、数据集、术语、示例
    ↓
DeepSeek：自然语言 → 结构化意图
    ↓
通用查询规划器
指标 + 维度 + 时间 + 筛选 + 排序 + TopN
    ↓
语义校验与数据集选择
    ↓
受控 SQL 编译器 + 专用复杂模板
    ↓
店铺权限注入 + SQL AST 安全检查
    ↓
查询执行器
├── 开发：DuckDB + Parquet
└── 生产目标：MaxCompute
    ↓
结果、口径、数据时间和必要的 SQL
    ↓
审计日志 + 监控指标
```

### 当前已跑通链路

```text
Web → Nginx → FastAPI → API Token
→ DeepSeek 结构化意图 → 通用查询规划/复杂专用模板
→ 店铺权限注入 → MaxCompute
→ 结果与 SQL → 审计与监控
```

通用查询规划器已完成第一版，基础经营问题已从“一题一 SQL”升级为受控组合；北极星、SKU 生命周期等复杂口径仍使用专用模板。当前最大差距是将现有关键词元数据检索升级为可量化评测的 RAG 语义检索。

### RAG 与通用查询规划器的区别

- RAG：为当前问题找到相关的指标、字段、表、口径和示例，解决“需要参考哪些知识”；
- 通用查询规划器：校验并编译指标、维度、时间、筛选、排序和 TopN，解决“查询应当怎样执行”；
- 两者相互配合，但不是同一个模块；必须先建立可靠的通用查询计划和语义约束，再扩展 RAG。

DataWorks 负责生产数据加工和调度；MaxCompute 负责生产数据存储与查询；AI 问数服务只负责理解问题、生成受控查询、执行只读查询和组织答案。

## 4. 当前数据范围

已归档到本地并上传 MaxCompute 的 6 张数据表：

1. `dws_brand_day_us`
2. `dws_sku_tag_day_us`
3. `ads_aws_sku_period_sales`
4. `ads_aws_sku_recap_month_detail`
5. `dwi_aws_sku_listing_date`
6. `dim_north_star_target`

真实数据只用于本地 SQL 执行、测试和评测，不进入 RAG 向量库，也不提交 Git。

RAG 使用数仓知识：表结构、表粒度、字段说明、指标口径、业务术语、关联关系和标准问数示例。

当前已知数据限制：`dws_brand_day_us` 是跨店铺品牌汇总表，没有 `shop_code`，因此运营人员不能在该表上安全执行店铺级隔离查询。正式数仓应增加口径可靠的店铺日汇总表。

### 阶段 5：通用查询规划器（已完成）

目标：从“一种查询模式一个 SQL 模板”升级为“有限语义范围内自由组合”。

实施顺序：

1. 定义通用查询计划：指标、维度、时间范围、筛选、排序和 TopN；
2. 建立指标 × 维度 × 数据集能力矩阵；
3. 支持最近 7/30/90 天、本周、上周、上月和指定月份；
4. 支持品牌、店铺、SKU、ASIN 和日期等维度；
5. 支持销售额、销量、订单数、退款金额和退款率等基础指标；
6. 通用生成 SELECT、WHERE、GROUP BY、HAVING、ORDER BY 和 LIMIT；
7. 将店铺权限注入通用查询计划或编译后的受控 SQL；
8. 保留北极星、生命周期等复杂问题的专用模板；
9. 增加组合查询、错误组合、澄清和权限测试。

第一批验收问题：

- 最近 30 天销售额排名前 3 的店铺是什么？
- 近一周整体退款率是多少？
- 最近 90 天各品牌销量是多少？
- 2026 年 8 月销售额最高的 10 个 SKU 是什么？

完成标准：上述问题及其合理同义问法，不新增完整 SQL 模板即可正确执行；不支持的指标与维度组合能解释原因或提出澄清。

验收结果：已完成 `QueryPlan`、指标/维度/数据集能力矩阵和通用 SQL 编译器；支持最近 7/30/90 天、数据最新周/上周、数据最新月/上月和指定月份。确定性查询规划评测 12/12 通过；DeepSeek 通用问题及同义问法评测 32/32 通过；69 项自动化测试和全仓 Ruff 检查通过。DuckDB 与 MaxCompute 端到端验收通过，缺少时间会澄清，不安全的店铺订单数聚合会解释限制，运营查询会强制注入授权店铺。

### 阶段 6：RAG 与语义检索评测（已完成）

目标：当元数据和示例增多时，只为当前问题召回相关知识，降低 Prompt 长度和选错指标/表的概率。

验收结果：已将 11 个指标、每张表、术语、跨表关系和 6 个标准问数示例拆成 32 个可检索文档；实现可解释的关键词+结构化关联检索；10 个标注问题上 Recall@5=89.67%、Recall@8=100%、MRR=0.90；RAG 上下文接入 DeepSeek 后，32 道通用问法仍为 32/32 通过。当前元数据规模不大，评测未证明需要 Embedding 或向量库，暂不引入。

## 7. 不可破坏的核心约束

- 数值答案必须来自查询结果，不能由大模型编造；
- DeepSeek 只负责问题理解，不直接执行 SQL；
- 权限由可信后端强制实施，不能依赖 Prompt 或模型自觉；
- 查询账号只读，只允许访问白名单数据集和字段；
- 同一指标在 DuckDB 与 MaxCompute 中必须保持相同业务口径；
- 时间边界、聚合粒度、去重规则和退款率分母必须明确；
- 真实数据、API Key、AccessKey、Token 和证书不得提交 Git；
- RAG 只保存数仓知识，不保存完整业务明细；
- 不为了堆技术名词提前引入 Agent、向量库或微调；
- 不用单次演示成功或意图准确率代替完整项目验收。
