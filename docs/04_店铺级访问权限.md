# 店铺级访问权限

## 目标

管理员可以查询已开放的全部数据；运营人员只能查询自己负责的 Amazon 店铺。角色和店铺范围由后端根据令牌确定，不能由浏览器或大模型指定。

## 当前配置

在 `.env` 中配置：

```env
# 已有的管理员令牌
API_AUTH_TOKEN=管理员随机长令牌

# 新增的运营令牌与授权店铺，多个店铺使用英文逗号分隔
OPERATOR_API_TOKEN=另一个随机长令牌
OPERATOR_SHOPS=CuspinArtGallery-US,VG Artisan-US
```

两个角色都在 Web 页面的“访问令牌”输入框使用自己的令牌。

## 后端执行规则

1. API 根据 `X-API-Key` 识别管理员或运营人员；
2. 管理员不追加店铺条件；
3. 运营人员的 SQL 由后端强制追加 `shop_code IN (...)`；
4. 未配置店铺、店铺配置非法或数据源没有店铺字段时返回 HTTP 403；
5. 审计日志记录身份、角色和店铺范围，但不记录令牌。

权限过滤发生在受控 SQL 生成之后、执行之前。DeepSeek 不负责生成权限条件，因此用户改变自然语言问法也不能绕过授权范围。

## 当前限制

`dws_brand_day_us` 是跨店铺品牌汇总表，没有 `shop_code`。运营人员查询依赖该表的品牌汇总、整体趋势或北极星问题时会被拒绝，管理员不受影响。正式数仓应新增包含 `shop_code` 的店铺日汇总表，既保证订单去重口径正确，也能支持店铺级隔离。

当前版本用一个管理员令牌和一个运营令牌验证权限链路。若面向多人正式使用，应将用户、角色、令牌摘要和店铺关系迁移到用户表或企业身份系统，不为每个人增加一组环境变量。

## 实际验收结果

- 运营令牌查询 SKU 销售排名成功，最终 SQL 包含授权店铺过滤，返回 10 行；
- 运营令牌查询无店铺字段的跨店品牌汇总，返回 HTTP 403；
- 管理员令牌执行同一个品牌汇总问题成功，返回 5 行；
- 审计日志已记录 `principal`、`role` 和 `shop_scope`。
