# AI 开发面试准备

## 1. 面试目标

本项目的定位是：基于 MaxCompute 数仓，为跨境电商运营人员建设企业内部 AI 智能问数应用。

面试重点不是背诵所有 Python 文件，而是能讲清楚：

- 业务问题是什么；
- 一条问题如何经过系统得到答案；
- 为什么采用 RAG、结构化意图和受控 Text-to-SQL；
- 如何保证 SQL 安全、数据权限和指标口径正确；
- 如何评测、部署和排查问题。

## 2. 必须掌握的主链路

```text
Web / Quick BI
→ FastAPI 认证与请求校验
→ 元数据 RAG 检索
→ LLM 结构化意图解析
→ Query Planner 查询规划
→ SQL Compiler / 业务模板
→ 店铺权限注入
→ SQL AST 安全校验
→ DuckDB 或 MaxCompute 执行
→ 结果摘要、图表、口径和 SQL
→ 审计日志与监控
```

口述版本：

> 运营人员输入自然语言问题后，系统先从指标、数据集、术语和示例中检索相关元数据，再由大模型将问题解析成指标、维度、时间和筛选条件。查询规划器校验问题是否在支持范围内并选择数据集，SQL 编译器生成受控查询语句，后端强制注入用户授权店铺并进行 AST 安全校验。通过后由 DuckDB 或 MaxCompute 执行，最后返回结果、指标口径和可追溯 SQL，并记录审计和监控信息。

## 3. 必须理解的概念

### LLM API

通过 API 调用大语言模型完成自然语言理解。本项目中模型只负责解析用户意图，不直接执行 SQL。

### RAG

先从业务知识库中检索相关内容，再把检索结果提供给模型，减少模型对指标名称、字段和业务口径的误解。本项目检索的是指标、数据集、术语、关联关系和标准示例，不是直接检索业务明细数据。

### Text-to-SQL

将自然语言问题转换为 SQL。本项目采用受控 Text-to-SQL：模型输出结构化意图，系统根据白名单和查询能力编译 SQL，而不是让模型自由生成任意 SQL。

### Query Planner

查询规划器负责判断指标、维度、时间和筛选组合是否支持，选择数据集，并生成后续 SQL 编译所需的查询计划。

### SQL Compiler

编译器把已经校验过的结构化查询计划翻译成目标数据库可以执行的 SQL。它不负责理解自然语言，也不允许模型自由拼接 SQL。

### AST 安全校验

SQLGlot 负责解析 SQL 并生成 AST；安全校验逻辑再检查 AST 是否为单条只读查询、是否只访问白名单表字段、是否包含危险操作或外部文件读取。

### Agent

Agent 通常包含任务规划、工具调用、状态管理和多轮执行。本项目主要是固定的受控查询工作流，不应把它包装成复杂自主 Agent；可以表述为 LLM 应用流程编排。

## 4. 高频设计问题

### 为什么不让大模型直接生成 SQL？

大模型可能生成不存在的表字段、错误的指标口径或危险 SQL。让模型只输出结构化意图，再由白名单、查询规划器和编译器生成 SQL，可以降低不可控性并方便测试和审计。

### 为什么需要 RAG？

模型本身不知道公司内部指标定义、表关系和字段含义。RAG 将相关业务元数据注入上下文，提升术语和指标匹配准确率；它不替代权限和 SQL 安全校验。

### 为什么复杂问题使用专用模板？

退款率、窗口排名、北极星达成率和生命周期判断包含明确业务口径。先用专用模板固化分子、分母、分区和并列处理规则，结果更稳定；成熟后再抽象为受控能力接入通用编译器。

### 权限如何保证？

用户身份由 Token 认证得到，后端根据身份强制注入授权店铺条件。权限不依赖 Prompt，也不接受用户自行传入的店铺范围；最终 SQL 还要经过安全校验。

### 为什么 AI 层尽量少做 Join？

复杂清洗、去重、订单粒度处理和指标加工应沉淀在数仓，保证口径统一和性能稳定。AI 层主要负责语义理解和查询编排。必要 Join 必须由语义层或专用模板定义，不能由模型临时自由拼接。

### 为什么返回 SQL？

运营端可以默认折叠 SQL；对数据分析师、开发和审计人员，SQL 提供口径追溯、问题排查和结果复核能力。展示层可以按角色控制是否显示。

## 5. 高频追问的回答框架

### 如果模型解析错了怎么办？

先用结构化输出和 Pydantic 模型约束格式，再由 Planner 校验指标和能力矩阵；不支持或信息不足时澄清或拒答，不进入 SQL 执行。通过评测集持续补充同义问法和提示词。

### 如果用户问了系统不支持的问题怎么办？

系统不会强行生成 SQL，而是返回澄清或“不支持当前查询能力”。后续根据高频需求新增指标元数据、查询能力或专用模板，并补充评测样例。

### DuckDB 和 MaxCompute 是什么关系？

两者是同一查询接口背后的不同执行引擎。DuckDB 加 Parquet 用于本地开发、离线测试和低成本演示；MaxCompute 用于连接云端数仓和生产数据。上层查询计划和安全规则保持一致。

### 如何评测系统？

分别评测意图解析、RAG Recall/MRR、查询规划、SQL 安全、权限隔离、引擎结果一致性和端到端响应时间，不能只看大模型主观回答是否“像正确答案”。

### 线上出现错误如何排查？

先看请求日志和审计记录，再判断错误发生在认证、RAG、意图解析、规划、SQL 安全、执行引擎还是结果格式化阶段；使用 request id、SQL 和数据集信息定位，并通过指标监控观察错误率、耗时和模型调用情况。

### 12.2 MaxCompute、DataWorks 与数仓

- 为什么选择 MaxCompute？和 Hive、Doris 有什么区别？

> maxcompute是云上的离数据平台，相比自建Hive集群，它不需要自行维护服务器、存储和计算资源，具备弹性扩缩容、权限管理和云平台运维能力。Doris更偏向实时或者低延迟的OLAP查询，适合报表、明细分析和交互式查询；

- 分区表如何设计？为什么按日期分区？

> 分区设计主要依据查询过滤条件、数据量和数据更新方式。对于按时间持续增长的事实表，通常按日期分区，便于增量写入和分区裁剪。
> 分区粒度要结合数据量、查询频率和分区数量。单日数据量较小且查询通常按周、月进行，可以考虑按周、月分区，对于需要按天查询的表，则保留日分区或增加日期字段辅助过滤；同时要避免分区过多导致元数据和小文件管理开销。

- DWD、DWS、ADS 分别解决什么问题？

> DWD是明细层，统一数据格式、粒度和主键，保留可复用的事实和维度数据；
> DWS是主题汇总层，围绕用户、订单、商品、广告等主题进行关联和聚合，沉淀可复用的主题模型；
> ADS是应用层，面向具体报表、看板或业务场景加工结果，减少应用侧重复计算。

- 如何处理数据重复、迟到、补数和重跑？

> 数据重复首先明确表粒度和业务唯一键，ODS尽量保留原始数据,DWD根据业务主键、事件时间或版本字段去重；
> 数据迟到时，先判断是采集延迟、上游补发还是调度问题，再根据影响范围重跑对应分区，对于有更新的数据，需要保留一定的回溯窗口；
> 补数时明确缺失日期、数据范围和依赖任务，按分区补跑并执行数据量、金额和主键校验；
> 重跑时优先保证任务幂等，避免重复写入；按照依赖顺序重跑受影响的分区和下游任务。

- 如何保证指标口径一致？

> 先和业务确认指标定义、统计粒度、时间范围、过滤条件和分子分母，并形成指标文档。然后将指标统一沉淀在数仓模型或指标层，避免不同报表各自计算；同时通过主键去重、订单状态过滤、数据对账和跨层校验验证结果，防止重复统计和口径发散。

- DataWorks 中如何配置依赖、重试、补数和告警？

> 在dataworks数据开发中配置节点、上下游依赖、调度周期、重试次数和超时时间；
> 在运维中心按日期或分区进行补数和重跑，并查看实例日志；
> 根据失败、延迟、数据量异常等条件配置告警，通知方式有钉钉、飞书、短信或其他企业通知渠道。

- 任务变慢时如何定位和优化？

> 我会先看dataworks实例日志和运行耗时，确认是数据读取、join、聚合、写入还是上游等待造成的。重点关注数据量突然增长、分区是否裁剪、是否发生全表扫描、join是否数据倾斜、是否存在笛卡尔积、小文件过多以及资源不足。

> 数据量突然增长：对比本次和历史的行数、文件大小和关键字段分布--重复写入、过滤条件失效、数据源新增，修复重跑
> 分区是否裁剪：检查SQL是否对分区字段加了过滤，查看执行计划或扫描数据量；--给分区字段加明确过滤条件；
> 全表扫描：看执行计划、输入数据量和扫描字节数；--补充分区过滤、只选择需要的列、尽早过滤数据；
> 数据倾斜：看各任务实例耗时，热点key、空值/默认值集中慢--检查key是否合理(重复膨胀)、小表join大表可广播，大表join大表可拆分热点key单独(热点key在两边表里某一张表体量较小，可以广播join)处理 或者加盐后分摊(两张表都需要加随机数，代价是膨胀)；
> 笛卡尔积：join条件是否缺失，前后行数是否膨胀；--补全正确的join条件，确认两边数据粒度和关联键；
> 小文件过多：查看分区文件数、平均文件大小和读取耗时，分区过细、写入并行度过高；--调整写入并行度；合并任务或者重写分区合并文件；对历史小文件做批量整理；
> 资源不足：看任务日志中的内存、CPU、并发或资源队列等待信息；--先优化SQL、减少扫描和中间数据；仍不足时再调整任务资源、并发或队列配置；
> SQL优化方法：分区(减少扫描数据量)；减少读取列数(select *)；尽早过滤数据(join/聚合前)；join前先聚合；避免不必要的join；优化join方式(广播join/数据倾斜/避免隐式转换)；减少重复计算(CTE/临时表/稳定复用沉淀宽表)；控制聚合和排序规模

- Flink 的 Checkpoint、状态和 Exactly-once 如何理解？

> 状态是flink计算过程中需要记住的信息；
> checkpoint是flink周期性保存的一致性快照，通常包括算子状态和消费位置。任务故障后，可以从最近的checkpoint恢复；
> Exactly- once：故障恢复后，每条事件对最终结果只产生一次有效影响(受数据源、checkpoint、sink影响)；

- Kafka 消息重复或乱序怎么处理？

> 落表时要明确主键、版本和更新语义，避免重复消费造成累计；

- Paimon 在实时数仓中解决什么问题？

> paimon是湖仓表格式，能够让流式写入和批式读取围绕同一份数据协作。用于实时数仓时，它可以承接Kafka/flink加工后的明细或变更数据，支持主键表的更新、流式写入和后续离线消费，减少实时链路和离线链路各维护一份数据的情况。

- 离线和实时链路如何保证最终口径一致？

> 首先统一业务定义、主键、时间字段、过滤规则和去重规则，不让实时和离线各自定义一套指标。然后明确两条链路的分工和数据范围。对账时按相同业务日期、相同粒度比较纪录和关键指标，关注迟到数据、重复事件、时区和状态变更，发现差异则溯源，处理规则和写入语义，回补重跑修正。

### 14.2 数据接入与同步

**MySQL、MongoDB 如何接入？**

> 在海外社交电商项目中，离线侧使用 Spark SQL 和 PySpark 抽取 MySQL、MongoDB 数据，完成字段类型转换、嵌套 JSON 解析、重复数据和异常值处理后落到 S3 ODS。之后再由下游 DWD 统一业务粒度和清洗规则。
> 全量一般用于初始化或历史回补，增量则按项目实际可用的更新时间、递增键或同步水位处理。

**为什么要区分 ODS 和 DWD 的清洗？**

> ODS 主要保留来源数据和抽取信息，保证可追溯和可回放，只做必要的技术转换；
> DWD 再按照业务主键、表粒度和状态规则做去重、标准化和异常处理。这样既不会丢失原始事实，也能让业务逻辑集中在可复用的明细层。

**JSON 嵌套和字段变化怎么处理？**

> 我会先保留原始 JSON 或原始字段，再解析下游需要的路径，对缺失、非法格式和类型不一致做显式处理。
> 字段变化要先评估 ODS、DWD 和下游报表影响，兼容字段按变更流程扩展，不能让类型转换失败静默变成错误数据。

**重复同步、失败和补数怎么处理？**

> 先根据任务水位和日志确认失败或重复的范围，目标表按分区覆盖、业务键去重或幂等合并，避免重跑造成重复累计。补数时明确日期、分区和下游依赖，按依赖顺序重跑，完成后检查行数、主键唯一性和核心金额指标。

**数据源新增字段或类型变化时，如何避免下游任务失败？**

> 我会先在ODS层保留原始数据，并通过字段变更检查识别新增字段、删除字段和类型变化。新增字段如果不影响现有逻辑，可以先兼容接入，再按变更流程拓展下游；类型变化则在ODS和DWD做显示转换(无法转换则纪录且告警)；上线前检查字段、SQL和依赖，小规模测试后再发布

### 17.3 建模与分层

**事实表和维度表的粒度怎么定？**

> 我会先用一句话定义一行数据代表什么，例如一条订单明细、一个用户当天行为或一个 SKU 一天的汇总。事实表围绕业务事件和度量建设，维度表描述用户、商品或创作者属性；主键、聚合方式和下游 Join 都必须遵守这个粒度。

**为什么订单表可能采用事务事实、累积快照或周期快照？你的场景如何选择？**

> 同一业务对象会按不同分析诉求分为三种事实表；
> 事务事实表：一行一次下单事件，只增不改；
> 累积快照事实表：一行一个订单，把下单到签收各环节的时间放在同一行，随流程更新；
> 周期快照事实表：一天一行，每天给在途订单记录一个状态快照。
> 我的场景一般选择事务事实表(订单项明细表)、周期快照事实表(SKU日汇总表)

**用户维度拉链表解决什么问题？何时需要保留历史属性？**

> 拉链表解决的是维度属性会变，但查历史事实必须用当时属性值的问题(覆写会冲掉历史口径、全量太占内存)
> 看这个属性和事实结合时是否必须用当时的值--用户等级(影响折扣)、业绩(销售归属)

**星型模型和宽表各适合什么场景？**

> DWD用星型，事实表和维度表分开，靠join关联，维度能复用；（也有维度退化，明细宽表)
> DWS是汇总宽表，粒度更粗，行数更少，把常用维度放进一行；

**DWD、DWS、ADS 的数据粒度和复用边界如何确定？**

> 边界可以用‘粒度和复用范围’来定，粒度越细 复用越广
> DWD保持最细业务过程粒度，不做聚合，限制上层分析自由的加工不做
> DWS是按主题加常用维度的轻度汇总(有两个以上下游要用)；
> ADS是按具体报表口径定制；

**维度退化、雪花模型、宽表冗余如何取舍？**

> 维度退化：看维度有没有单独落表的必要(除了编号还有没有其他属性值得单独维护)
> 雪花模型：维度表里带层级的部分再单独拆出为子维度表--比如类目体系；使用的两种情况：维度很深且多个维度表复用、维度表本身大需拆出低频字段
> 宽表冗余：稳定的高频字段可以冗余

**你的 DWD/DWS 模型怎么落地？**

> 社交电商项目中，我开发了用户、创作者、订单和行为等 DWD 明细表，再建设用户活跃、创作者分析和广告主经营等 DWS 主题模型。DWD 负责统一格式、主键和异常处理，DWS 负责按主题和时间粒度沉淀可复用的汇总指标，供运营分析和 Retool 查询。

**采购商画像为什么没有单独建设 DWS？**

> 这个项目的核心粒度是采购商，标签场景相对明确，已有 DWD 明细能够满足加工需求，所以直接在 Doris 中关联 DWD 并沉淀 ADS 画像宽表，减少中间层维护成本。Doris 的列式存储、列裁剪和分析执行能力适合这类宽表查询；如果未来有多个场景复用同一批聚合结果，再增加公共 DWS 更合适。

**多张事实表关联如何避免重复统计？**

> 先确认各表粒度和关联基数，不能因为都有订单号或用户 ID 就直接 Join。通常先把各事实表聚合到共同粒度，再关联维度或主题表，并比较 Join 前后的行数、主键数和指标总额，防止一对多或多对多导致数据发散。

### 17.4 指标与质量

**如何治理销售额、退款率和广告费？**

**业务口径变更如何处理？**

> 先确认新口径的生效时间和是否要求历史可比，再评估受影响的明细、汇总和 BI 主题。如果要统一历史结果，就按影响分区回刷并做新旧结果对账；如果新旧口径并行，则标注版本和生效日期，避免报表混用。

### 17.5 性能与分区

**如何设计分区？**

> 我会结合数据增长方式、主要查询条件、单分区数据量和补数习惯选择粒度。时间字段通常便于增量和范围查询，但不一定固定按天；如果日数据量和查询习惯不适合日分区，可以采用周或月分区，同时保留日期字段支持业务过滤，重点是避免分区过细和扫描过大之间失衡。

**任务变慢如何排查？**

> 我先看 DataWorks 或 Oozie 的实例日志、执行阶段和上游等待情况，再检查分区裁剪、扫描列数、Join 基数、数据倾斜、小文件和资源使用。SQL 侧优先增加有效分区过滤、提前过滤和聚合、减少无用列，确认小表广播或热点 Key 处理是否适合；优化后比较耗时、扫描量和关键指标结果。

**大表 Join 和数据倾斜怎么处理？**

> 先确认 Join Key 和两边粒度，排除一对多造成的行数膨胀；然后先过滤、先聚合，减少 Shuffle。小表场景可以评估广播，大表场景要看热点 Key 和实例耗时，确认是倾斜后再拆分热点或加盐，并在汇总时恢复原业务粒度。

### 14.6 调度与运维

**为什么要把销售、退款、广告和利润链路解耦？**

> 这些数据源的到达时效不同，如果全部串成一条链路，退款、广告或利润慢源会阻塞核心销售产出。我在经营数仓中按数据到达时效拆分主链路和补充链路，配置分级调度，让销售相关结果先稳定产出，补充数据到达后再更新相应主题，同时通过对账和异常校验保证最终结果完整。

**任务失败或数据迟到怎么处理？**

> 先确认是依赖未完成、数据未到、任务本身失败还是结果质量异常，再根据影响范围确定重跑分区。修复后按依赖顺序补跑，不直接盲目全量重跑；目标任务要具备分区覆盖或主键幂等能力，补跑后核对行数、主键和核心指标。

**如何设置告警？**

> 对核心销售链路延迟、任务失败、分区缺失、数据量异常和指标对账失败设置高优先级告警；可自动恢复或非核心任务的短时波动可以汇总通知。告警需要包含任务、分区、影响范围和处理建议，避免只有“任务失败”而没有定位信息。

### 17.9 第 15 节其余问题补充口述版

**增量同步依赖更新时间、递增 ID、Binlog 还是其他机制？为什么？**

> 这要看源表的更新特征。主要是追加数据且有连续递增键时，可以按 ID 增量；存在更新记录时，优先使用可靠的更新时间并保留回溯窗口；如果必须捕获更新和删除，则考虑 CDC 或变更日志。选择标准是不能漏数、能处理迟到和重复，并且方便失败后按水位恢复。具体项目中我会按实际使用的同步工具和字段回答。

**源端更新、删除如何同步到数仓？**

> 更新记录按业务主键和更新时间取最新，或者在需要历史追溯时维护版本。删除需要源端提供删除标记或 CDC 事件；如果没有可靠删除信息，就通过定期全量对账或快照比对发现。ODS 保留来源记录，DWD 再按业务规则处理生效状态。

**抽取失败、断点续跑和回补怎么处理？**

> 先根据任务日志和同步水位确认失败范围，修复原因后从上一次成功水位或受影响分区续跑。目标写入要按分区覆盖、主键幂等或版本合并，避免重复写入。历史回补前先确认影响日期和下游依赖，回补后检查记录数、主键和核心指标。

**事实表和维度表为什么这样设计？**

> 事实表记录订单、行为等可度量业务事件，维度表描述用户、商品、创作者等分析对象。这样设计可以把事件度量和属性复用分开，便于按不同维度分析，也能通过明确粒度避免重复统计。具体表设计会先确定一行代表什么，再确定主键、分区和更新方式。

**用户维度拉链表解决什么问题？**

> 拉链表用于保留用户属性的历史变化，例如用户等级或所属区域变化。通过生效时间和失效时间，可以还原某个历史时点的属性，避免用当前属性错误解释历史订单。如果业务只关心当前状态，则不必为了分层而强行建设拉链表。

**维度退化、雪花模型和宽表如何取舍？**

> 退化维度适合与事实紧密相关、单独复用价值不高的标识；雪花模型适合层级复杂且需要统一维护的维度；宽表适合固定、高频、低延迟的分析场景。实际会在公共层保持清晰模型，在 ADS 或看板层适度宽表化，平衡复用性、性能和维护成本。

**如何处理迟到维度、历史属性和事实修正？**

> 迟到维度可以先关联未知成员，维度到达后再补关联；历史属性是否回溯取决于业务是否需要历史时点分析，需要时使用拉链或版本字段；事实修正则按受影响日期和分区回刷，并同步更新下游汇总和报表。

**退款率、广告费等指标的时间口径如何确定？**

> 先确认业务使用的是下单日、支付日、发货日、退款发生日还是账单日，再统一到指标文档和公共模型。退款率还要明确退款金额归属日期、订单状态和销售额分母；广告费要明确平台账单日期、币种和店铺归属，不能只按字段名称直接汇总。

**去重依据是什么？不同来源订单 ID 能直接关联吗？**

> 不能默认直接关联。先确认订单 ID 的来源和唯一范围，跨平台时通常要结合平台、店铺等字段形成复合键，或通过映射关系关联。去重还要定义保留规则，例如按更新时间或版本取最新，并检查去重前后的行数、金额和主键分布。

**如何选择数据质量规则？**

> 按字段和业务重要性选择：主键检查唯一性，必填字段检查非空，金额数量检查范围，分区检查完整性，核心指标检查环比波动，分层模型做记录数和金额对账。阈值要结合历史波动设置，既能发现异常，也避免大量误报。

**数据量突然翻倍或指标为零如何定位？**

> 先对比异常分区和最近正常分区的记录数、主键数、空值率和关键字段分布，再检查是否重复同步、分区条件失效、Join 行数膨胀、状态枚举变化或上游数据缺失。确认原因前先阻止异常结果进入下游，修复后按影响分区重跑并重新对账。

**分区裁剪失效通常是什么原因？**

> 常见原因是漏写分区过滤、对分区字段套函数、隐式类型转换，或者过滤条件无法下推。我会查看 SQL 和执行计划，改成对分区字段的直接范围过滤，再对比实际扫描分区和数据量。

**如何判断是全表扫描、数据倾斜、小文件还是资源不足？**

> 看执行计划、扫描量、任务各阶段耗时、并行实例输入输出和文件数量。扫描量异常大通常是分区裁剪失效；少数实例明显慢通常要排查热点 Key；文件数量很多且单文件很小是小文件；内存错误、资源队列等待或并发不足则更像资源问题。

**小文件如何产生和合并？**

> 常见原因是分区过细、写入并行度过高或频繁小批次写入。新任务可以调整并行度和批次，历史分区按平台能力合并或重写。治理后检查文件数、平均大小、读取耗时和数据完整性，不能只看文件数下降。

**SQL 优化前后比较哪些指标？**

> 我会比较执行耗时、扫描数据量、Shuffle 或中间数据量、各阶段资源使用和失败重试情况，同时核对输出行数、主键数和关键指标。只有性能改善且结果口径一致，才算优化有效。

**MaxCompute、Hive、Doris 的适用场景有什么区别？**

> Hive 更像基于 Hadoop 的离线数仓方案，需要自行管理底层集群；MaxCompute 是云上托管平台，适合海量离线加工和批处理；Doris 是 MPP 分析数据库，更适合低延迟的交互式查询和报表。我的项目中 MaxCompute 负责经营数仓加工，Doris 更偏采购商画像和分析查询场景。

**DataWorks 或 Oozie 如何配置依赖和调度？**

> 我会按数据链路把采集、ODS、DWD、DWS 和 ADS 拆成任务节点，配置上下游依赖、运行周期、超时、重试和告警。下游任务只有在上游成功且分区数据就绪后才运行，补数时按日期和依赖范围重跑，而不是直接全量执行。

**如何设置重试、补数和告警？**

> 临时网络或资源失败可以设置有限次数重试，业务数据缺失和质量异常则需要告警并人工确认。补数时指定受影响的日期或分区，按依赖顺序执行并对账；告警内容要包含任务名、分区、失败原因和责任人，方便快速处理。

**任务成功但数据错误，如何阻止继续传播？**

> 在任务状态之外增加数据质量门禁，例如分区完整性、行数波动、主键唯一、非空和核心指标对账。质量检查失败时阻止下游发布或标记不可用，并在修复和回补后重新校验，避免“任务成功但业务数据错误”。

**生产故障如何止损、回补和通知？**

> 先确认影响的表、分区和下游报表，暂停错误结果继续传播并通知业务方；再查看日志、依赖和源数据定位原因，修复后按影响范围补跑，最后做分层对账和结果复核，同时记录故障原因和改进措施。

**BI 看板慢时如何区分 SQL、模型还是展示层问题？**

> 先单独执行 BI 数据集 SQL，看底层扫描量和耗时；如果 SQL 本身慢，就优化分区、模型和 Join；如果 SQL 快但页面慢，再检查筛选器、图表数量、并发、缓存和展示组件。这样可以先定位瓶颈层，再决定优化数据还是 BI 配置。

**如何控制不同业务角色的数据范围？**

> 角色和数据范围应在后端或数据访问层执行，不能只依赖前端隐藏。经营数仓和 AI 问数中可以按店铺或业务归属注入过滤条件，敏感字段按角色脱敏或不返回，并通过不同角色的实际查询结果验证权限隔离。

- `list`、`dict`、`set` 的区别；

> `list` 是有序、可重复的集合，适合保存一组有顺序的数据；`dict` 以键值对保存数据，适合通过字段名快速获取值；`set` 是不重复的无序集合，常用于去重和判断成员是否存在。例如问数结果的多行数据可以用 `list[dict]` 表示，授权店铺集合则可以用 `set` 做去重和快速判断

- 异常处理；

>     result = runner.execute(sql)
> except TimeoutError:
>     logger.exception("query timeout")
>     return error_response("查询超时")

- 文件和 JSON 处理；

> 文件处理时使用 `with` 自动关闭文件，并明确编码；JSON 解析后先校验必需字段和数据类型，不能直接假设模型一定返回正确结构。对于模型返回内容，我会先提取 JSON，再用数据模型进行结构校验，字段缺失或类型错误时进入澄清或失败流程。

>     config = json.load(file)

- FastAPI 如何定义接口；

> FastAPI 通过路由函数定义 HTTP 接口，用 Pydantic 模型校验请求和响应结构，用依赖注入处理认证、配置或公共上下文。项目中的 `/ask` 接收用户问题和可选上下文，完成认证后调用问数服务，最终返回固定格式的问数结果。

>     return service.ask(request, principal)

- API Token 如何认证；

> 请求通过请求头携带 Token，后端读取 Token 后进行安全比较，并根据 Token 映射出用户角色和授权店铺。认证通过后才进入查询流程，权限范围由后端保存和注入，不能接受用户在请求体中自行传入的店铺范围。Token 应放在环境变量或密钥管理系统中，不能提交到 Git 或写死在代码里。

> 首先设置连接超时和读取超时，避免请求无限等待；超时后根据错误类型做有限次数重试，并使用退避时间避免瞬间重复请求。超过重试次数后返回友好的“模型服务暂时不可用”，同时记录模型、耗时和 request id，不能把异常堆栈直接返回给用户。
> 只对网络抖动、连接失败或临时服务错误进行有限重试；认证失败、参数错误、额度不足和业务拒答不应该重试。重试要设置次数上限和退避策略，并记录每次调用耗时，避免一次用户请求产生大量重复调用和成本。
>
> 我会先区分 SQL 参数错误、权限错误、连接错误、超时和服务端故障。SQL 或权限问题通常直接拒绝并记录原因；临时连接或服务异常可以有限重试；查询超时则终止执行并返回提示。日志中保留数据集、耗时、错误类型和 request id，但不向用户暴露 AccessKey 等敏感信息。
