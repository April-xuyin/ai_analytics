## 复盘第一遍：讲清楚完整链路

运营人员输入问题
→ 请求经过Nginx统一入口，进入到FastAPI验证身份，发起请求
→ RAG检索相关指标、表、口径和示例，将数仓知识和原始问题一起发给大模型
→ 大模型(DeepSeek)解析成结构化意图(不同的说法映射为同一标准词)
→ 查询规划器进行语义校验，选择数据集和查询方式
→ 通用编译器生成受控SQL
→ 注入授权店铺范围
→ 查询执行器(SQL AST安全校验、方言翻译)
→ DuckDB或MaxCompute执行，返回数据行
→ 回答/结果组装(返回数据行列、摘要、口径和SQL)
→ 记录审计日志与监控指标

> prompt有四段
>
> 1. 解析用户的经营分析问题。
>    用户问题：最近30天销售额最高的10个SKU是什么？

> 4. 业务规则（易错点）：

##### 2.3 查询规划：app/query_planning/planner.py

###### 职责：检查这个问题是否属于系统支持的查询能力

###### 做了什么：检查了

- sales_amount 是否是合法指标；
- seller_sku 和 asin 是否是允许的维度；
- last_30_days 是否是支持的时间范围；
- 是否能从某个数据集查询；
- 是否需要澄清。

###### 输出：如果检查通过，它会生成结构化的查询计划，如下：

数据集：dws_sku_tag_day_us

指标：sales_amount

维度：seller_sku、asin

时间：最近30天

排序：降序

限制：10

* 如果检查到用户问了当前系统不支持的指标，Planner会让系统返回澄清或拒答，而不是继续下一步生成 SQL。

##### 2.4 生成SQL：app/sql/compiler.py(generator.py)

###### 职责：接收已经校验通过的查询计划，生成受控 SQL

###### 做了什么：按固定骨架分块拼装SQL

> * SELECT = 维度 + 指标表达式（从 `plan.metric_expressions` 取）
> * FROM = `plan.dataset`
> * WHERE = `1 = 1` + 时间条件 + 过滤条件，用 AND 连起来
> * GROUP BY / HAVING / ORDER BY / LIMIT —— 有才拼，没有就是空
> * 其中 **时间条件是它自己换算的** ：规划器只输出 `time_range="last_30_days"` ，compiler 按它算出 `days - 1 = 29`，拼成 `stat_dt >= (SELECT MAX(stat_dt) - INTERVAL 29 DAY FROM 表)`。

###### 输出：

> SELECT seller_sku, asin, ROUND(SUM(TRY_CAST(ordered_product_sales AS DOUBLE)), 2) AS sales_amount
> FROM **dws_sku_tag_day_us**
> WHERE 1 = 1
> AND **stat_dt >= (SELECT MAX(stat_dt) - INTERVAL 29 DAY FROM dws_sku_tag_day_us)**
> GROUP BY **seller_sku, asin**
> ORDER BY **sales_amount DESC**
> LIMIT **10**
>
> - 表名来自数据集白名单；
> - 指标表达式来自指标元数据；
> - 维度来自允许的字段；
> - 时间条件由系统生成；
> - 排序和 LIMIT 由结构化参数控制；
> - 用户不能直接注入任意 SQL。

##### 2.6  SQL 安全校验 app/query/sql_security.py

职责：判断上游传过来的SQL允不允许执行。

做了什么（5条检查）

* 合法性：能不能把SQL文本变成语法树
* 单条查询：必须恰好一条语句，而且这条语句必须是"查询"类型 。
* 确认是否白名单表：扫到**两处** `dws_sku_tag_day_us`（外层 FROM + 子查询 FROM），两处都在 → 过
* 函数（非封锁名单函数）：扫到 `ROUND`、`SUM`、`MAX`、`CAST`，都不在封锁名单里 → 过
* 字段白名单：`seller_sku` / `asin` / `stat_dt` / `ordered_product_sales` / `shop_code` 都在 datasets.yaml 里 → 过

失败时抛`SqlSecurityError` → runner 转成 `QueryError` → 500。

##### 2.7 查询执行 maxcompute_runner.py

###### 职责：真正算出数字

###### 输入：校验过后的SQL

###### 做了什么：

* 去空白、去结尾分号；
* AST安全校验（AST检查被包含进执行器里）
* 检查`max_rows` 合法
* 方言翻译 `_to_maxcompute_sql()`：

> `TRY_CAST(... AS DOUBLE)` → `CAST(... AS DOUBLE)`
> `MAX(stat_dt) - INTERVAL 29 DAY` → `DATEADD(MAX(stat_dt), -29, 'dd')`

* 提交SQL到maxcompute → 等跑完 → 拉取结果
* 按 schema 取列名，逐行读，读到第 10 行就停

###### 输出：`list[dict]`，最多 10 行

> [{"seller_sku": "A5B382A507", "asin": "B0DHNZ6FWZ", "sales_amount": 24360.86}, ...]

###### 失败时：全抛 `QueryError` → [service.py:114](vscode-webview://02oesfpo03pl0d75drgg7feo9hn2e68ubithcrlqghle947flnbk/ai_analytics/app/questions/service.py#L114) → 500

两种情况：校验不过（表/字段不在白名单、读了文件）、执行失败（语法错、表不存在、超 60 秒）。

##### 2.8 返回问数结果：app/questions/models.py

###### 职责：查询完成后，把结果封装成固定结构返回

###### 做了什么：

定义了一个 dataclass `AnalyticsAnswer`：11 个字段 + 一个 `to_dict()`；请求过来的时候再往里面填值

###### 输出：`AnalyticsAnswer` 对象

> "message": "查询成功",

###### **最后main.py再把这个对象`AskResponse(**answer.to_dict())`转成 HTTP JSON 响应，返回给 Web 页面。**

## 第三遍复盘

四个关键设计问题：

- 为什么不让DeepSeek直接生成并执行SQL？
- RAG和查询规划器有什么区别？
- 为什么店铺订单数会被拒绝？
- 为什么运营角色不能查询无法按店铺隔离的品牌汇总表？



1. 为什么不让 DeepSeek 直接生成并执行 SQL？

三层理由，从轻到重：

正确性：模型会编字段名、编表名、编口径，而且编得很像真的，数字没法信任；
安全：直接执行的 SQL 能写 DROP/DELETE，能 read_csv 读服务器文件，用户还能靠改提问绕过权限；
可追溯：SQL 由"模板 + 元数据"生成，才能拿去白名单校验、才能复用、才能解释这个数字是怎么算出来的。
所以模型只做归一化（自然语言 → 结构化意图），bailian.py:56 的 system prompt 里就写死了"只返回合法JSON，不生成SQL"。SQL 是确定性代码的事。

2. RAG 和查询规划器有什么区别？

RAG	查询规划器
给谁用	给模型看	给系统把关
干什么	挑出相关的指标口径、表结构、示例，塞进 Prompt	判断这个组合能不能查、去哪张表查
输出	知识文档（不是数据）	QueryPlan（不是 SQL）
不管会怎样	模型可能选错指标	模型可以指向任意表和字段
一句话：RAG 管"模型知不知道"，Planner 管"系统许不许"。 RAG 是软的——它只是上下文，模型可以不听；Planner 是硬的——planner.py:52 那里不合法就直接抛异常，全链路终止。

3. 为什么店铺订单数会被拒绝？

因为两张表各缺一半：

order_count 只在 dws_brand_day_us 上，而这张表没有 shop_code 维度；
有 shop_code 的 dws_sku_tag_day_us 没有 order_count。
更根本的是口径问题：SKU 日表一行是一个 SKU，一个订单含多个 SKU 时会被重复计数，SUM 出来是虚高的。所以这不是"暂时没做"，是"这么算就是错的"——planner.py:84-89 直接拦掉，返回 unsupported。

4. 为什么运营角色不能查询无法按店铺隔离的品牌汇总表？

因为 dws_brand_day_us 没有 shop_code 字段，WHERE shop_code IN (...) 注入不进去。一旦放行，运营看到的就是全公司所有店铺的汇总——不做隔离 ≠ 少看一点，而是多看很多。

所以 _apply_shop_scope 先检查 SQL 里用到的表在不在"可按店铺隔离"的名单里（只有 dws_sku_tag_day_us、ads_aws_sku_period_sales、dwi_aws_sku_listing_date 三张），不在就 403 拒答。宁可拒答，也不放行——数据泄露不可逆，拒答只是体验问题。

3 和 4 是同一件事的两面：dws_brand_day_us 缺 shop_code（所以不能隔离），dws_sku_tag_day_us 缺 order_count（所以不能汇总）。两张表的能力互补但不重叠。
