# 通用查询规划器

## 1. 为什么需要它

旧流程可以理解不同问法，但最终只能进入若干预先写好的完整 SQL 模板。新增“店铺维度”或“最近 7 天”时，即使 DeepSeek 正确识别了意图，也可能没有可执行模板。

通用查询规划器把常见分析问题拆成可组合部件：

```text
指标 + 维度 + 时间 + 筛选 + 排序 + TopN
```

复杂的北极星目标、生命周期等问题仍保留专用模板；基础聚合问题由通用编译器生成 SQL。

## 2. 当前模块

- `metadata/query_capabilities.yaml`：唯一的能力矩阵，声明每张表支持哪些指标和维度；
- `app/query_planning/planner.py`：校验组合并选择数据集，输出 `QueryPlan`；
- `app/query_planning/compiler.py`：把已校验的计划编译成受控 SQL；
- `app/sql/generator.py`：优先路由复杂模板，其余基础聚合交给通用规划器；
- `app/intent/bailian.py`：让 DeepSeek 输出店铺维度及 7/30/90 天时间范围。
- `evals/generic_questions.yaml`：保存标准问题、真实运营式同义问法和预期查询结构。

## 3. 一次查询如何执行

以“最近 30 天销售额排名前 3 的店铺”为例：

```text
DeepSeek意图
metric=sales_amount
dimensions=[shop_code]
time_range=last_30_days
sort=descending
limit=3
        ↓
能力矩阵判断 dws_brand_day_us 没有 shop_code
        ↓
选择 dws_sku_tag_day_us
        ↓
编译 SELECT / WHERE / GROUP BY / ORDER BY / LIMIT
        ↓
权限层追加运营人员可访问的 shop_code
        ↓
DuckDB或MaxCompute执行
```

## 4. 为什么订单数暂不支持店铺通用聚合

`dws_sku_tag_day_us` 按 SKU 汇总。同一订单可能包含多个 SKU，直接对多个 SKU 的 `order_cnt` 求和可能重复计算订单。

因此能力矩阵没有声明该表支持通用 `order_count`。这不是程序遗漏，而是为了保护指标口径。正式方案应使用带店铺粒度且已按订单去重的店铺日汇总表。

## 5. 当前已支持

- 时间：最近 7、30、90 天、数据最新周/上周、数据最新月/上月以及指定月份；
- 维度：品牌、店铺、SKU、ASIN、日期，具体组合受能力矩阵约束；
- 指标：销售额、销量、退款金额、退款率；品牌日表额外支持订单数；
- 操作：筛选、分组、升降序、TopN和销售额阈值；
- 已完成本地 DuckDB 与 MaxCompute 的首批端到端验收。

## 6. 首批验收结果

- “最近 30 天销售额排名前 3 的店铺是什么？”：选择 `dws_sku_tag_day_us`，按店铺分组，返回 3 行；
- “近一周整体退款率是多少？”：选择 `dws_brand_day_us`，使用最近 7 天窗口，返回 1 行；
- “最近 90 天各品牌销量是多少？”：选择 `dws_brand_day_us`，返回 5 行；
- “2026 年 8 月销售额最高的 10 个 SKU 是什么？”：选择 `dws_sku_tag_day_us`，返回 10 行；
- “上周各品牌销售额是多少？”：按最大数据日期的上一自然周查询，返回 5 行；
- “上个月各品牌销售额是多少？”：按最大数据日期的上一自然月查询，返回 5 行。
- 容器重建后已通过 Web/API → DeepSeek → MaxCompute 真实链路复验。

指定月份验收曾发现 DeepSeek 将时间返回为对象、并误选 `monthly_sales`。现已在模型输出之后进行确定性规范化：明确的自然月销售额使用 `sales_amount + stat_month`，非法时间类型由规划器拒绝，不再产生未捕获异常。

## 7. 后续与 RAG 的衔接

- 通用规划器作为确定性执行边界继续保留；
- RAG 只为 DeepSeek 召回相关元数据和示例，不绕过能力矩阵、权限或 SQL 安全校验；
- 后续每新增基础指标或维度，需先补能力矩阵和评测再开放查询。

## 8. 安全边界验收

- 未指定时间的“哪个品牌销售额最高”返回澄清问题，不扫描全部历史数据；
- “最近30天各店铺订单数”不会从 SKU 日表直接累加，因为一张订单可能包含多个 SKU；系统返回口径说明且不生成 SQL；
- 运营人员询问“最近30天销售额排名前3的店铺”时，后端仍强制注入授权店铺范围，实际只返回授权店铺；
- 即使 DeepSeek 没有主动澄清，查询规划器也会再次校验时间与指标/维度组合；
- 自动化测试：69 项通过，Ruff 全仓检查通过。

## 9. 通用规划器组合评测

评测文件：`evals/query_plans.yaml`。它不调用 DeepSeek，因此不产生模型费用，专门验证结构化意图之后的规划、编译和本地执行。

```bash
uv run python scripts/evaluate_query_plans.py
```

当前结果：

```json
{
  "total": 12,
  "passed": 12,
  "accuracy": 1.0
}
```

覆盖范围：

- 品牌多指标经营概况；
- 店铺销售额 TopN；
- SKU 销售额与退款金额组合；
- 品牌退款率；
- 品牌筛选、销售额阈值、升降序和指定月份；
- 缺少时间范围；
- 不安全的店铺订单数；
- 未知维度和未知筛选条件；
- 合法 SQL 的 DuckDB 实际执行。

安全回归规则：基础指标一旦被通用规划器拒绝，不允许回退到可能忽略筛选条件的旧模板。

## 10. DeepSeek 自然语言组合评测

评测文件：`evals/generic_questions.yaml`。每类能力同时包含标准问法和更接近运营人员的同义问法，检查指标、维度、时间、筛选、数据集选择和 SQL 结构。

```bash
uv run python scripts/evaluate_generic_questions.py
```

当前结果：32/32 通过，各分项准确率均为 100%。评测会真实调用 DeepSeek，但不执行业务 SQL；MaxCompute 执行另通过容器 API 抽样验收。

## 11. RAG 检索基线与评测

- `metadata/relationships.yaml`：维护跨表关联和业务口径；
- `metadata/examples.yaml`：维护标准问法和预期查询计划；
- `app/retrieval/`：输出有文档 ID、类型、得分和命中词的可解释检索结果；
- `evals/retrieval_questions.yaml`：10 个标注问题的 Recall@K 验收集；
- `scripts/evaluate_retrieval.py`：运行本地检索评测。

```bash
uv run python scripts/evaluate_retrieval.py
```

当前基线结果：Recall@5=89.67%、Recall@8=100%、MRR=0.90。元数据共 32 个检索文档，当前不需要额外引入 Embedding 和向量数据库。
