# 生产验收与运维手册

## 1. 部署前门禁

```bash
uv sync --frozen
uv run ruff check app scripts tests
uv run pytest
node --check web/app.js
uv run python scripts/predeploy_check.py --env-file .env
docker compose config --services
docker compose build
```

`predeploy_check.py` 只输出缺失的配置名和错误原因，不打印任何密钥值。当前本地生产模拟配置已通过该检查。

GitHub Actions 配置位于仓库根目录 `.github/workflows/ai_analytics_ci.yml`，在提交或 PR 改动 `ai_analytics/` 时自动执行代码检查、测试、离线评测、前端语法检查和 Docker 构建。

## 2. 发布流程

1. CI 全部通过后，用 Git 提交号作为镜像标签，例如 `ai-analytics:20260928-<commit>`。
2. 设置 `APP_IMAGE` 为待发布标签，执行 `docker compose up -d --no-build`。
3. 等待容器健康，验证 `/health`、`/me`、`/metrics`。
4. 用管理员执行一条跨店查询，用运营令牌执行一条授权店铺查询。
5. 确认新的审计记录和 Prometheus 请求计数已生成。

## 3. 回滚演练

发布前记录当前 `APP_IMAGE` 标签为 `PREVIOUS_APP_IMAGE`。如新版健康检查失败或核心问数失败：

```bash
APP_IMAGE=<PREVIOUS_APP_IMAGE> docker compose up -d --no-build --force-recreate
docker compose ps
curl --fail http://127.0.0.1:8080/health
```

回滚只替换应用和 Nginx 容器，不修改 MaxCompute 数据。`logs/` 通过挂载保留，便于回滚后查看失败请求。

## 4. 密钥轮换演练

1. 在 DeepSeek 或 RAM 控制台创建新密钥，保留旧密钥。
2. 在受控配置中替换对应值，生成新的管理员/运营长令牌。
3. 运行 `predeploy_check.py`，再重建容器。
4. 验证新令牌成功、旧令牌返回 401，并用新的 DeepSeek/MaxCompute 密钥各执行一次请求。
5. 验证成功后立即禁用旧密钥。如验证失败，在旧密钥仍有效时恢复配置。

本项目不把密钥写入镜像、Git、日志或评测报告。

## 5. 故障处理

| 现象 | 先检查 | 处置 |
|---|---|---|
| 502/504 | `docker compose ps`、应用健康检查 | 查应用日志，必要时回滚 |
| DeepSeek 超时 | 审计耗时、模型服务状态 | 重试单条请求，不重复执行 SQL |
| MaxCompute 超时 | `query_error`审计、SQL、时间范围 | 缩小时间/维度，检查套餐资源 |
| 运营返回 403 | `/me` 中的角色和店铺 | 修正 `OPERATOR_SHOPS`，不绕过权限层 |
| 数值可疑 | 指标口径、数据日期、追溯 SQL | 运行双引擎对照，暂停发布新口径 |

## 6. 本地验收与 ECS 的边界

当前已完成本地 Docker + Nginx + FastAPI + DeepSeek + MaxCompute 的生产模拟验收。ECS 实际迁移只需安装 Docker、上传代码/镜像、注入密钥、放行 80/443 并配置 HTTPS；在真正完成公网部署前，项目简历口径应写“完成可迁移的生产化方案和本地生产模拟”。
